# Audit architecture et frontières de modules — zylo-office

Date : 2026-10-08. Mode : lecture seule (aucun code modifié, aucune donnée lue, aucun secret reporté).
Périmètre : `zylo-office-backend` (app/, .importlinter, CI, config) et `zylo-office-frontend` (src/, configs de ports).
Chemins relatifs : backend = `zylo-office-backend/`, frontend = `zylo-office-frontend/`.

## Vérifications effectuées

- **import-linter** : `lint-imports` n'est pas dans le PATH et le binaire du `.venv` est cassé. Le contrôle a été relancé avec `/usr/bin/python3` et les paquets du `.venv` (`PYTHONPATH`, cache dans le scratchpad). Résultat : **10 contrats KEPT, 0 broken** (120 fichiers, 362 dépendances).
- **Graphe de dépendances** : parcours AST de `app/` (imports de premier niveau et imports paresseux), agrégé par paquet, avec détection de cycles. Ce n'est pas un résultat de grimp.
- **Lecture ciblée** : `.importlinter`, `CLAUDE.md`, `ARCHITECTURE.md`, `app/core/config.py`, `app/modules/zylo_liquid/*`, `app/location|alerts|notifications/*`, frontend `src/app`, `src/core`, `src/shared`, `src/modules`, `package.json`, `README.md`, `Dockerfile`, `.env.example`, `.github/workflows/`.

### Réponse à la question directe : zylo_liquid dépend-il d'internes de files ou de preview ?

- **files** : non, pour les internes. `zylo_liquid` n'importe que `app.files.service` (`app/modules/zylo_liquid/service.py`), `app.files.schemas` (`service.py`, `router.py`) et `app.files.permissions` (`roles_seed.py`, `seed.py`). Aucun import de `app.files.models` ni `app.files.router`. Le contrat `zylo-liquid-files-through-service-only` le garantit, et il passe.
- **preview** : **aucun module « preview » côté backend** (aucune occurrence). Côté frontend, le composant `src/shared/ui/FilePreviewModal.tsx` est partagé, mais il fait un `fetch` direct (voir ARC-011).
- **location / alerts** : `zylo_liquid` n'accède pas aux `models` de ces capacités (contrats KEPT). Les `permissions` et `service` sont utilisés, ce qui est conforme.

Points clés :
1. Les règles d'architecture sont **vérifiées localement mais pas en CI** : `.github/workflows/ci.yml.disabled` contient `lint-imports`, mais le workflow est désactivé. Le `CLAUDE.md` affirme pourtant le contraire.
2. Les contrats `.importlinter` ne couvrent que `zylo_liquid` et les capacités. **`zylo_tanker` n'est couvert par aucun contrat d'accès aux tables**, et il n'existe aucun contrat d'acyclicité : des cycles entre paquets existent (capacités <-> zylo_liquid/zylo_tanker, socle <-> identity/rbac).
3. `app/modules/zylo_liquid/service.py` fait **15 681 lignes et 504 fonctions** (plus `schemas.py` à 4 162 lignes et `router.py` à 3 289). C'est le principal point de dette.
4. Les défauts de configuration (secrets de repli codés en dur, ports qui divergent entre README, package.json, CLAUDE.md et Dockerfile) rendent le déploiement et les environnements dev/prod peu fiables.
5. Un dump SQL (`backups/*.sql.gz`) est **suivi par git** malgré le `.gitignore`.

## Notes sur les faux positifs et limites

- Les 10 contrats `.importlinter` passent : les problèmes ci-dessus ne sont **pas** des violations de contrats existants, sauf ARC-006 et ARC-007 (absence de contrat) et ARC-008/ARC-009 (`ignore_imports` ou cycles non vérifiés).
- Le graphe a été calculé par AST, imports paresseux inclus. Les cycles sont au niveau des paquets, pas forcément des imports circulaires au chargement de module.
- `CLAUDE.md:27` (« capacité → modules INTERDIT ») contredit la pratique documentée dans `ARCHITECTURE.md` (Location, Alertes et Notifications dépendent de `Truck`/`Vessel`/`Station`). Ce point est traité en documentation (voir ARC-007 pour la lacune réelle) : la règle doit être mise à jour, non le code.
- Hors périmètre : la couverture de tests, la sécurité applicative au-delà de la configuration, et la qualité du code frontend (non lintée dans cet audit).
