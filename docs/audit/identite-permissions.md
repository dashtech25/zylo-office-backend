# Audit identité, auth et permissions (IAM)

**Date** : 2026-10-08
**Périmètre** : `app/identity`, `app/rbac`, `app/modules_registry`, `app/auth`, `app/core/security.py`, `app/core/config.py`, routes d'attribution de `app/billing`, personnel de station `app/modules/zylo_liquid` ; frontend `src/core/auth`, `src/core/api/client.ts`, `src/core/api/rbac.ts`, `src/core/rbac`, `src/app/(app)/users|roles|organizations`.
**Méthode** : lecture statique seule. Aucun test lancé, aucune requête exécutée, aucune donnée lue. Les scénarios d'exploitation sont **déduits du code** et doivent être confirmés par un test d'intégration avant correction.
**Chemins** : relatifs à `zylo-office-backend/` (sauf mention `frontend`).

**Légende**
- Priorité : **P0** bloque la priorité n°1 ou faille exploitable en production ; **P1** à corriger avant la prochaine livraison ; **P2** dette ou risque à planifier ; **P3** durcissement.
- Gravité : Critique, Élevée, Moyenne, Faible.

**Synthèse** : 24 problèmes (P0 : 2, P1 : 7, P2 : 10, P3 : 5). Le défaut le plus grave est IAM-001 : l'isolation entre organisations repose sur un en-tête non vérifié contre le chemin de l'URL.

## Modèle actuel

Tables (préfixe `zylo-office-backend/`) :
- `organization` (id, name, slug unique, status, soft-delete) : `app/identity/models.py:11-17`.
- `user` (id, email unique, hashedPassword, fullName, status, mustChangePassword, profil) : `app/identity/models.py:20-41`. Global, sans organisation.
- `organizationUser` (organizationId FK, userId FK, unique) : `app/identity/models.py:44-54`. Appartenance, non vérifiée pour les attributions (IAM-004).
- `role` (organizationId FK, code, name, unique(org, code)) : `app/rbac/models.py:12-23`. Aucune notion de module.
- `permission` (code unique `module.ressource.action`, moduleCode texte, catalogue global) : `app/rbac/models.py:26-32`.
- `rolePermission` (roleId FK, permissionId FK, unique) : `app/rbac/models.py:35-45`.
- `userRole` (userId, organizationId, roleId, resourceType texte, resourceId UUID, unique à 5 colonnes) : `app/rbac/models.py:48-75`. NULL = organisation entière.
- `userPermissionGrant` (organizationId, userId, permissionId, effect allow|deny, portée, origin, delegatedFromGrantId FK auto-référencé, grantedByUserId, validFrom/validUntil, revokedAt) : `app/rbac/models.py:78-121`.
- `module` (code unique, name, version) et `organizationModule` (organizationId, moduleCode FK, status active|inactive|trial) : `app/modules_registry/models.py:12-35`.
- `refreshToken` (userId FK, tokenHash unique, expiresAt, revokedAt) : `app/auth/models.py:12-19`.
- `plan` et `subscription` (billing) : plans globaux.

Flux réels :
1. Inscription : `POST /api/v1/auth/register` crée un `user` actif, sans organisation (`app/auth/service.py:20-29`).
2. Connexion : `POST /auth/login` renvoie un access token (15 min) et un refresh token (30 jours), rotation à chaque refresh (`app/auth/service.py:45-82`).
3. Création d'organisation : `POST /organizations` crée l'organisation, l'appartenance, un rôle `owner`, 11 permissions du socle et l'attribution owner (`app/identity/service.py:75-99`, `OWNER_DEFAULT_PERMISSIONS` l.30-42).
4. Activation d'un module : `POST /modules/organizations/{id}/activate` (`MODULE_MANAGE`, en-tête) seed les rôles par défaut du module et accorde ses permissions au owner (`app/modules_registry/service.py:96-155`).
5. Création d'un utilisateur : seule voie = personnel de station `POST /zylo-liquid/station-staff` (`app/modules/zylo_liquid/service.py:8150-8176`) : user + appartenance + fiche + rôle scopé à la station.
6. Attribution : `POST /rbac/organizations/{id}/user-roles` (`ROLE_MANAGE`) ; grants : `POST /rbac/organizations/{id}/grants` (`GRANT_MANAGE`).
7. Vérification : `require_permission` lit l'en-tête (IAM-001) puis `user_has_permission` (`app/rbac/service.py:92-131`) : rôles (UserRole x RolePermission, portée) ∪ grants allow, `deny` prioritaire.
8. Frontend : `GET /rbac/.../me/permissions` alimente `PermissionContext.can()` (indicatif, IAM-014).

## Écart vs cible (priorité n°1)

| Étape cible | Réel | Écart |
|---|---|---|
| 1. Créer une organisation | Fait (le créateur devient propriétaire) | Quota absent (IAM-017) |
| 2. Créer des utilisateurs (par le propriétaire) | Seulement personnel de station, lié à une station | Pas de création au niveau organisation ni invitation (IAM-006) |
| 3. Choisir un utilisateur dans un module | Aucune affectation utilisateur -> module | Absente (IAM-005) |
| 4. Droits propres au module, par organisation | `permission.moduleCode` existe ; rôles non liés à un module ; activation par organisation OK | Rôles multi-modules possibles (IAM-005) |
| 5. Droits différents par module pour un même utilisateur | Impossible nativement : portée libre, `resourceId` UUID, `Module.code` texte | Portée module à créer (IAM-005) |
| 6. Décision d'autorisation unique | Trois mécanismes, en-tête contre chemin | IAM-001, IAM-013 |
| 7. Appartenance avant droits | Non vérifiée pour les attributions et grants | IAM-004 |
| 8. Session et mot de passe | Pas de révocation, drapeau non appliqué côté serveur, pas de rate limit | IAM-007, IAM-008, IAM-010 |

Ordre de correction proposé : IAM-009 (confirmer et verrouiller les secrets), IAM-001 + IAM-018 (isolation et tests), IAM-004, IAM-005 et IAM-006 (modèle de la priorité n°1), puis IAM-007 et IAM-008.
